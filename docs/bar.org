#+description: Widgets, dropdown panels, toasts and the plugin system behind them

* The gowl bar
:PROPERTIES:
:CUSTOM_ID: the-gowl-bar
:END:

The bar is a gowl module that draws one or two status bars, a dropdown panel under whichever widget you click, and a stack of notification toasts. Everything it shows comes from a *plugin*: a small object with a poll function, a label, and optionally a panel. The shipped widgets --- the clock, the system readings, the network panel --- use exactly the same interface a plugin you write does, and there is no private path they take that yours cannot.

This document covers configuring the bar, then writing a plugin.

** At a glance
:PROPERTIES:
:CUSTOM_ID: at-a-glance
:END:

- Three regions per bar --- left, centre and right --- with a *centre anchor* so one widget stays dead centre no matter what appears beside it.
- Two bars: top and bottom. Both are optional; both are configured the same way.
- A click on a widget opens its *panel*: a dropdown the plugin describes and the bar renders, hit-tests, scrolls and gives keyboard navigation to.
- *Toasts*: on-screen notifications the bar owns. A toast can name a panel, so "Wi-Fi is not configured" becomes one click away from the network dropdown.
- Plugins load from a search path --- =~/.config/gowl/bar-plugins/= by default, extendable with =plugin-dir= --- as a compiled =.so= *or as a plain =.c= file*, compiled on demand through crispy --- no build system, no install step, and =gowl bar-plugin-reload= to pick up an edit without restarting.
- Every colour is a named *theme role* resolved out of the session palette, so one =palette:= setting restyles the bar, its panels, its toasts, and every third-party widget in it.
- A plugin that faults is caught, unloaded and reported rather than taking the session down. See [[#containment][Containment]] for what that does and does not promise.

** Configuring the bar
:PROPERTIES:
:CUSTOM_ID: configuring-the-bar
:END:

*** Widget lists and regions
:PROPERTIES:
:CUSTOM_ID: widget-lists-and-regions
:END:

#+begin_src yaml
modules:
  bar:
    enabled: true
    height: 30
    widgets-left: "tags title"
    widgets-center: "clock"
    widgets-right: "cpu memory disk:/var battery network audio"
    center-anchor: "clock"
#+end_src

Each list is space separated and in order. The *right* region reads outward: the first entry ends up furthest right, which is how every dwm-descended status list has always read.

=center-anchor= names one widget in the centre region. That widget is centred on the monitor and the rest of the centre region packs around it. Without an anchor the centre region is centred *as a group*, which means the clock slides sideways every time something appears next to it.

A =widgets:= key with no region keeps its historical meaning --- the right-hand status list --- so a configuration written before regions existed needs no changes.

*** What happens to the shipped layout
:PROPERTIES:
:CUSTOM_ID: shipped-layout
:END:

With no configuration at all the bar shows a shipped layout: the tag row and window title on the left, the clock anchored dead centre, and =cpu memory disk battery tailscale= on the right.

=tailscale= is in that list because it can answer for itself whether it belongs: hidden where Tailscale is not installed, and carrying the set-up flow where it is but no tailnet has been joined. See [[#tailscale][Tailscale]].

That layout is a starting point, not a base to add to. *The first configuration that names any widget list replaces it wholesale* --- including the regions that configuration does not mention.

This matters on upgrade. A configuration written before regions existed sets only =widgets:=, and its list usually ends with a clock. If the shipped centre clock survived that, the bar would show the time twice. It does not: the shipped layout is cleared first.

A pre-regions configuration additionally gets =tags title= put back on its left, because the bar it was written for drew the tag row and the window title unconditionally rather than listing them. So an untouched old configuration comes out looking exactly as it did, plus panels and toasts.

After that first configuration the bar behaves incrementally: a later call setting only =widgets-right= leaves the left and centre alone.

*** Widget specs
:PROPERTIES:
:CUSTOM_ID: widget-specs
:END:

A widget is written =name=, =name:parameter= or =name:parameter@seconds=:

| Spec              | Meaning                                            |
|-------------------+----------------------------------------------------|
| =cpu=             | The =cpu= widget with its own defaults             |
| =disk:/var=       | The =disk= widget watching =/var=                  |
| =weather:Berlin@600= | Weather for Berlin, refreshed every ten minutes |
| =cmd:~/bin/pomo@5=   | A command's first line of output, every five seconds |

The interval suffix uses the *last* =@= in the spec, so =cmd:ssh me@host@30= parses the way you meant it.

The whole spec is the widget's identity, so two =disk:= widgets on different mounts are separately addressable --- by =gowl bar-panel=, by a toast's panel target, and by per-widget settings.

*** Per-widget settings
:PROPERTIES:
:CUSTOM_ID: per-widget-settings
:END:

Two forms, both in the same block:

#+begin_src yaml
modules:
  bar:
    # A colour, by palette role or by hex literal.
    cpu-color: green
    memory-color: blue

    # Anything else, as <widget>.<key>.
    clock.format: "%a %b %d  %H:%M"
    title.max-width: "480"
    network.ping-host: "1.1.1.1"
    weather.units: "m"
#+end_src

*** The bottom bar
:PROPERTIES:
:CUSTOM_ID: the-bottom-bar
:END:

One module owns both slots, and a YAML block names one module --- so the bottom bar's keys are the same keys with a =bottom-= prefix:

#+begin_src yaml
modules:
  bar:
    enabled: true
    widgets-right: "cpu memory clock"

    bottom-enabled: true
    bottom-height: 26
    bottom-widgets-left: "user host"
    bottom-widgets-right: "network podman media"
    bottom-tags.visible: "false"
#+end_src

A configuration pushed from Elisp or from =config.c= uses =position: bottom= instead and arrives as its own call; both routes end in the same place.

*** Filtering notifications

The bar drops a toast before it is ever shown when it matches
=notify-discard=, and while =notify-dnd= is on it drops everything that
does *not* match =notify-dnd-allow=. All three are ordinary bar
settings, so they live in the gowl config next to the layout:

#+begin_src yaml
modules:
  bar:
    notify-discard: "^Spotify;screenshot saved"
    notify-dnd: false
    notify-dnd-allow: "battery;^Calendar"
#+end_src

Patterns are newline- or semicolon-separated case-insensitive regexes,
tested against the toast's summary and body. An unparsable pattern is
reported once and skipped rather than quietly matching nothing --- a
filter that silently does nothing is worse than no filter, because it
looks like it is working.

Discard and Do Not Disturb are different things on purpose. A discarded
notification is gone in both modes; that is for the sender never worth
hearing from. Do Not Disturb suppresses the interruption for a while,
and the allow list is what keeps it usable --- a mode that hides
absolutely everything is one people switch off and never switch back on.

cmacs has the same two lists on its own side, in the notification
subsystem rather than the bar: =cmacs-notify-daemon-discard-rules= and
=cmacs-notify-daemon-dnd-allow-rules=, matching on =:app=, =:summary=,
=:body= and =:urgency=. There the discard happens before the
notification is recorded at all, so a discarded one never reaches the
history, the log or the hook.

*** Hover tooltips

Resting the pointer on a widget names it. The text is whatever the
plugin last set through =gowl_bar_plugin_set_tooltip()=, falling back to
the plugin's registered title, and it appears after a short delay ---
sweeping the pointer across the bar on the way somewhere else should not
flash six tips. A click or an opening panel dismisses it, and the tip
itself is click-through: it explains the thing under it, so a click
belongs to that thing.

A =toggle= takes =tooltip=, or =tooltip-on= and =tooltip-off= for text
that changes with the state. This matters more for toggles than for
anything else --- a toggle is a single glyph whose meaning lives
entirely in its configuration, so without hover text the widget that
most needs naming is the one that cannot be named. The shipped caffeine
toggle sets both.

*** Theming
:PROPERTIES:
:CUSTOM_ID: theming
:END:

The bar inherits the session palette, so the first thing to reach for is not a bar setting at all:

#+begin_src yaml
palette:
  name: mocha        # or macchiato, frappe, latte, dwm
#+end_src

Every widget, panel and toast follows it, including plugins you wrote and plugins somebody else wrote. On top of that, =theme-*= keys adjust the bar specifically:

| Key                          | Meaning                                              |
|------------------------------+------------------------------------------------------|
| =theme-<role>=               | Override one colour role, e.g. =theme-accent: mauve= |
| =theme-metric-<name>=        | A pixel metric, e.g. =theme-metric-panel-width: 400= |
| =theme-scale=                | Multiply every metric at once, for a HiDPI session   |
| =theme-font=                 | The body font, as a Pango description                |
| =theme-icon-font=            | The font used for glyph icons                        |

Roles: =base=, =mantle=, =crust=, =surface=, =surface-alt=, =overlay=, =text=, =subtext=, =muted=, =accent=, =red=, =green=, =yellow=, =blue=, =mauve=, =teal=, =peach=, =pink=, =sapphire=, =sky=, =lavender=, =flamingo=, =rosewater=, =maroon=.

Metrics: =radius=, =pad-x=, =pad-y=, =gap=, =row-height=, =item-pad=, =item-gap=, =border=, =panel-width=, =panel-offset=, =shadow=, =toast-width=.

The legacy =bg-color= and =fg-color= keys still work; they set the =base= and =text= roles.

** The shipped widgets
:PROPERTIES:
:CUSTOM_ID: the-shipped-widgets
:END:

Run =gowl bar-plugins= for the live list, which includes anything you have installed. What ships:

*** Window manager
| Widget   | Shows                       | Click                        |
|----------+-----------------------------+------------------------------|
| =tags=   | The dwm-style tag row       | View (left) / toggle (right) |
| =title=  | The focused window's title  | ---                          |
| =layout= | The active layout's symbol  | Cycle layouts                |

=title= takes =delimiters=, =palette= and =delimiter-color= to colourise a path or a buffer name by segment, and =max-width= to stop a maximised terminal's title pushing everything else off the bar.

*** System
| Widget    | Shows                          | Panel               |
|-----------+--------------------------------+---------------------|
| =cpu=     | Processor utilisation          | System              |
| =memory=  | Memory in use                  | System              |
| =swap=    | Swap in use                    | System              |
| =disk=    | Free space on a mount          | System              |
| =load=    | One-minute load average        | System              |
| =temp=    | Package temperature            | System              |
| =gpu=     | GPU utilisation                | System              |
| =io=      | Block read and write rates     | System              |
| =uptime=  | Time since boot                | System              |

| =user=    | User name                      | ---                 |
| =battery= | Charge, with a bolt when charging | Power            |
| =power=   | Session power actions          | Power               |

All of the system widgets open the *same* panel, with the hero changed to match whichever one you clicked. A click on the memory widget and a click on the temperature widget should both take you to the place where you can see what the machine is doing.

Colour is computed from pressure --- text, then peach past 75%, then red past 90% --- unless you set an explicit =<widget>-color=, which always wins.

*** Network
| Widget      | Shows                      | Panel                                    |
|-------------+----------------------------+------------------------------------------|
| =network=   | SSID or address            | Ping, rates, totals, signal, DNS, Wi-Fi list |
| =net=       | Throughput                 | Network                                  |
| =ip=        | The interface's address    | Network                                  |
| =wifi=      | Signal strength            | Network                                  |
| =vpn=       | Whether a tunnel is up     | ---                                      |
| =bluetooth= | Connected device, or off   | Power, scan, paired devices              |
| =tailscale= | Tailnet state              | Peers, exit nodes, sign-in               |

=bluetooth= runs =bluetoothctl= on the worker thread --- adapter state, paired and connected devices --- and connects or disconnects from the panel. It *hides itself where there is no adapter*, so a desktop without one carries no dead icon, and it ships in the default layout for the machine that does have one. =command= overrides the tool.

The network panel reads what the kernel already knows, and uses =nmcli= only for the parts that genuinely need it --- so the readings still work on a machine with no NetworkManager, and only the actions disappear.

**** Tailscale
:PROPERTIES:
:CUSTOM_ID: tailscale
:END:

The =tailscale= widget ships in the default layout and shows itself wherever Tailscale is installed --- including on a host that has never joined a tailnet, where it carries the set-up flow.

On a Tailscale-native image that is the case you most want a prompt for: the machine is one click from being on the tailnet and simply has not been told to. Hiding the widget there would hide the button.

| Host                    | Widget                      | Panel                                |
|-------------------------+-----------------------------+--------------------------------------|
| Not installed           | hidden                      | ---                                  |
| Installed, never joined | shown, yellow, =set up=     | *Join a tailnet*                     |
| Join waiting on browser | shown, yellow               | *Open the sign-in page*, and the URL |
| Joined, tailnet down    | shown, dimmed               | the switch, peers, exit nodes        |
| Joined, running         | shown, teal                 | the switch, peers, exit nodes        |

Yellow rather than grey for the never-joined case, because it is something to do rather than something broken.

***** Joining
:PROPERTIES:
:CUSTOM_ID: tailscale-join
:END:

*Join a tailnet* runs =tailscale up=. That command publishes its sign-in URL through =tailscale status --json=, so the next poll picks it up and the panel turns into the open-the-link view on its own --- nothing has to parse the command's output. The panel then offers to open the link, shows it in full so it can be read, and can copy it to the clipboard.

That is also the one case that raises a toast, wired to this widget's panel: a join waiting on a browser is time-sensitive and easy to miss. A host that has simply never joined gets no toast --- the yellow widget is the invitation, and a notification every login telling you that you *could* set up Tailscale is nagging.

Bringing a device up normally needs root. The set-up panel offers *Allow without sudo*, which runs =pkexec tailscale set --operator=$USER= once; after that, joining works from the panel alone. It uses =pkexec= so the prompt is the desktop's, not a terminal the bar has no way to give you.

***** Overriding
:PROPERTIES:
:CUSTOM_ID: tailscale-show
:END:

#+begin_src yaml
widgets-right: "tailscale:never cpu memory"
#+end_src

| Mode     | Means                                            |
|----------+--------------------------------------------------|
| =auto=   | the default: shown wherever Tailscale is installed |
| =always= | always shown, even without Tailscale installed   |
| =never=  | never shown                                      |

The widget keeps polling while hidden, so installing Tailscale makes it appear within a poll rather than at the next login.

Membership is read from =HaveNodeKey= in =tailscale status --json=, which stays true across a =tailscale down= and goes false only on a host that never joined or was logged out. The whole reply is read once per refresh and every field pulled out of it, rather than shelling out per value.

**** Clipboard history

Lists what the =clipboard= module has kept. =j= and =k= move, =RET=
picks, and two keys belong to this panel specifically: =y= copies the
focused entry back to the clipboard and =x= (or =Delete=) forgets it.
Deleting a password out of the history is the case this exists for, so
it is one key rather than a menu.

Those two arrive through =panel_key=, a vtable entry the host offers
after its own navigation declines a key. The host keeps =Escape=, =j=,
=k=, =Tab= and =Return= because they mean the same thing in every panel;
=x= does not, and would be alarming in a Wi-Fi list.

The widget reads the store's index directly on the worker thread rather
than going through the module's IPC, because reading it is a file read
and IPC would have to happen on the compositor thread.

The same history is an editable buffer in cmacs --- =M-x
cmacs-clipboard=, where killing a line and saving deletes that entry.

**** Notifications

The daemon is cmacs-side elisp and the widget does *not* ask it anything: its poll, its panel and its clicks all run on the compositor thread, and a round trip into the Lisp VM from there is a deadlock waiting for a quiet afternoon. So the daemon *pushes* --- =cmacs-notify-bar-mode= writes =notifications.count=, =.dnd= and =.last= through =gowl-bar-configure= whenever they change, and the widget renders what it was last told. A session with no daemon pushes nothing and the widget reads zero, which is quiet rather than wrong.

Unread means "arrived since you last looked", not "still on screen" --- a notification that timed out unseen is exactly the one a backlog exists for.

The panel's three controls are settings (=command-open=, =command-clear=, =command-dnd=), defaulting to =emacsctl eval= calls into =cmacs-notify-bar-*=, so a different daemon drops in without touching the widget.

**** Screenshot
:PROPERTIES:
:CUSTOM_ID: screenshot
:END:

=screenshot= ships in the centre of the default layout, immediately left of =recorder= --- still capture next to moving capture. Clicking it opens a panel offering *Screen*, *Window* and *Selection*; the result is written to =~/Pictures/Screenshots= and placed on the clipboard, so it can be pasted straight into a chat or a buffer.

It prefers the compositor's own =screenshot= module, which cmacs loads by default:

- *Window* arms a picker: the window under the pointer is highlighted and the one you click is captured. It does *not* photograph the focused window --- whatever you used to ask for the shot (the panel, the keybind) is itself the reason something else has focus, so the focused window is the one answer that is almost always wrong. gowl knows where the window is, so no rectangle has to be drawn round it either.
- *Selection* is an in-compositor rubber band --- drag to choose, =Escape= or right-click to cancel --- so it needs no =slurp=. Both interactive modes dim the desktop the moment they arm, so an armed capture never looks like a keybind that did nothing, and the widget lights up while one is in progress.
- The panel closes before anything is captured, and the capture waits a frame for it to actually leave the scene. A capture renders the scene as it stands, so a screen shot taken from an open dropdown would otherwise contain the dropdown.
- The clipboard is gowl's own selection, offered as =image/png=. No =wl-copy=, and no second process sitting around holding the offer.

Without that module it falls back to =grim= (plus =slurp=, and =wl-copy= for the clipboard if it is installed), and the panel says which of those is missing. The fallback still picks a window rather than settling for the focused one: gowl feeds =slurp= a box for every visible window on stdin, so it snaps to whole windows and returns the one clicked. It only names a missing tool when the fallback is what would actually run --- with the module loaded, =grim= is never reached and reporting it absent would be a lie.

=directory= overrides where a fallback capture is written; the module's own =save-directory= governs the native path.

The same three captures are on the keyboard by default, reaching the module by name through =ipc_command= --- so the binds need to know nothing about how a capture works, and are inert rather than broken in a session with no screenshot module:

| Key                 | Captures            |
|---------------------+---------------------|
| =Super+Shift+S=     | a dragged selection |
| =Super+Print=       | the focused window  |
| =Print=             | the whole screen    |

=Escape= cancels a selection in progress, and so does =screenshot-cancel=. The other names are =screenshot-area= (=screenshot-select=), =screenshot-window=, =screenshot-screen= (=screenshot=) and =screenshot-all= for every monitor stitched together; all of them work from =gowl <command>= too.

The wheel over =audio= changes the volume and over =display= changes the brightness. A bar widget may claim the wheel without a modifier only because the pointer is over it --- there is no ambiguity about what it means.

*** Generic
These are how you add something the shipped set does not cover, without writing any C:

#+begin_src yaml
modules:
  bar:
    widgets-right: "button:screenrec toggle:caffeine cmd:~/bin/pomo@10 spacer label"

    # A button runs a command.
    button.icon: "⏺"
    button.command: "wf-recorder -g \"$(slurp)\""
    button.command-right: "pkill -INT wf-recorder"
    button.tooltip: "Record a region"

    # A toggle asks a command for its state and runs another to change it.
    toggle.state-command: "pgrep -x wl-idle-inhibit"
    toggle.command-on: "systemd-inhibit --what=idle sleep infinity &"
    toggle.command-off: "pkill wl-idle-inhibit"
    toggle.icon-on: "☕"
    toggle.icon-off: "☕"
    toggle.color-on: "green"
#+end_src

| Widget    | Purpose                                                     |
|-----------+-------------------------------------------------------------|
| =button=  | A glyph that runs a command; separate left/right/middle     |
| =toggle=  | A stateful button, polled by =state-command=                |
| =cmd=     | The first line of a command's output                        |
| =label=   | Static text                                                 |
| =spacer=  | Fixed empty width, optionally a divider rule                |

** Panels
:PROPERTIES:
:CUSTOM_ID: panels
:END:

Clicking a widget with a panel opens it under that widget (or above it, for a bottom bar). Clicking the same widget closes it; clicking a different one switches. A click anywhere else dismisses it and is swallowed, so the click that closed a dropdown does not also land in the application behind it.

While a panel is open:

| Key             | Does                          |
|-----------------+-------------------------------|
| =Escape=        | Close                         |
| =Down= / =j= / =Tab= | Next interactive row     |
| =Up= / =k=      | Previous row                  |
| =Return= / =Space= | Activate the focused row   |

The wheel scrolls a panel taller than the screen. Sliders are draggable.

Open a panel without the pointer:

#+begin_src sh
gowl bar-panel network      # open the network dropdown
gowl bar-panel              # close whatever is open
#+end_src

** Toasts
:PROPERTIES:
:CUSTOM_ID: toasts
:END:

The bar owns an on-screen notification stack, drawn on the OVERLAY scene layer so it is visible over a fullscreen window --- which is when a critical notification matters most.

#+begin_src sh
gowl bar-notify 'Backup finished|1.4 GB written'
gowl bar-notify 'Wi-Fi is not configured|No known network is in range|network'
gowl bar-dismiss
#+end_src

The third field is a *panel target*. A toast with one is clickable, and clicking it opens that widget's dropdown --- a notification that hands you the thing that fixes it, rather than telling you to go find it. A toast with no panel but a command runs the command instead.

A toast raised at critical urgency never expires on its own and cannot be pushed off the stack by later chatter. That is what a plugin-crash report uses.

** Writing a plugin
:PROPERTIES:
:CUSTOM_ID: writing-a-plugin
:END:

Copy =data/example-bar-plugin.c= into =~/.config/gowl/bar-plugins/= and it works. That file is a complete, commented pomodoro timer with a panel; this section is the contract behind it.

*** The shape of one
:PROPERTIES:
:CUSTOM_ID: the-shape-of-one
:END:

A plugin is a struct of function pointers and a descriptor:

#+begin_src C
#include <gowl/barkit/gowl-bar-plugin.h>
#include <gowl/barkit/gowl-bar-plugin-proxy.h>
#include <gowl/barkit/gowl-bar-registry.h>

static void
hello_poll(GowlBarPlugin *plugin, gpointer data)
{
	(void)data;
	gowl_bar_plugin_set_label(plugin, "hello");
}

static const GowlBarPluginVTable hello_vtable = {
	sizeof(GowlBarPluginVTable),
	NULL, NULL,            /* create, destroy */
	NULL, NULL, NULL,      /* activate, deactivate, configure */
	NULL, hello_poll, NULL,/* interval, poll, poll_async */
	NULL, NULL,            /* measure, draw */
	NULL, NULL,            /* click, scroll */
	NULL, NULL,            /* panel, action */
	NULL, NULL             /* panel_opened, panel_closed */
};

static const GowlBarPluginDesc descs[] = {
	{ GOWL_BAR_PLUGIN_ABI, "hello", "Hello", "A greeting", "1.0.0",
	  &hello_vtable, NULL, { NULL, NULL, NULL, NULL } }
};

G_MODULE_EXPORT const GowlBarPluginDesc *
gowl_bar_plugin_query(guint *n_descs)
{
	*n_descs = G_N_ELEMENTS(descs);
	return descs;
}
#+end_src

Every slot may be =NULL=; the bar uses its default. The minimum viable plugin is a =poll= that calls =gowl_bar_plugin_set_label()=, and it gets measurement, drawing, hover, and the panel machinery for free.

=size= must be the first member and must be =sizeof= the struct *as your file sees it*. That is what lets the vtable grow without breaking a plugin built against an older gowl: the bar checks every callback lies inside the size you declared before calling it.

One file may publish several plugins. They are then one compile and one reload rather than several.

*** Which thread you are on
:PROPERTIES:
:CUSTOM_ID: which-thread
:END:

This is the one rule that matters more than the rest.

- =poll= runs on the *compositor's dispatch thread*. It may read =/proc=, do arithmetic, and call the setters. It may **not** spawn a process, touch the network, or block on anything --- that thread holds the lock every editor primitive needs, so blocking it freezes the editor as well as the bar.
- =poll_async= runs on a *worker thread*. This is where a subprocess, an HTTP request or a slow file read belongs. It may call =gowl_bar_plugin_set_label()=, =set_icon()=, =set_color()= and =set_tooltip()= --- all of which are thread-safe --- and nothing else.
- =draw=, =measure=, =click=, =scroll=, =panel= and =action= all run on the dispatch thread, and are subject to the same rule as =poll=.

If you need a subprocess in response to a click, use =gowl_bar_plugin_spawn()=, which is fire-and-forget, or =gowl_bar_plugin_queue_work()= to run something blocking on a worker.

*** Talking to a CLI
:PROPERTIES:
:CUSTOM_ID: plugin-json
:END:

Plenty of things a widget wants to show come from a command with a
=--json= mode. Linking a full JSON parser into a bar plugin for three
scalars is more dependency than the job deserves, and hand-rolling a
scanner is how a plugin ends up reading the *next* object's field when
its own is absent --- silently, with a plausible-looking answer.

=gowl/barkit/gowl-bar-json.h= reads named fields by anchoring on a
complete ~"key":~ match and brace-matching object values:

#+begin_src C
g_autofree gchar *state = NULL;
g_autofree gchar *self = NULL;

state = gowl_bar_json_string(reply, "BackendState");
self  = gowl_bar_json_object(reply, "Self");   /* bounded */
name  = gowl_bar_json_string(self, "HostName");

gowl_bar_json_foreach_object(reply, "Peer", collect_peer, &state);
#+end_src

It is not a JSON parser: it does not validate, build a tree, or address
a path. What it does is fail by returning =NULL= rather than by
returning somebody else's value. The Tailscale widget is built on it.

*** Colour
:PROPERTIES:
:CUSTOM_ID: plugin-colour
:END:

Name a role, never a hex literal:

#+begin_src C
gowl_bar_plugin_set_color(plugin, GOWL_BAR_COLOR_PEACH);
#+end_src

A widget that writes =#fab387= stays that colour when the user switches to Latte. A widget that names =GOWL_BAR_COLOR_PEACH= follows. The shipped plugins are held to this by a source guard.

*** Panels
:PROPERTIES:
:CUSTOM_ID: plugin-panels
:END:

A plugin *describes* its dropdown; the bar draws it. That is what makes a plugin from outside the tree look and behave exactly like a shipped one, and what lets the panel layer gain a feature --- scrolling, keyboard navigation --- without any plugin changing.

#+begin_src C
static GowlBarPanel *
my_panel(GowlBarPlugin *plugin, gpointer data)
{
	GowlBarPanel *panel;
	GowlBarPanelItem *item;

	panel = gowl_bar_panel_new();
	gowl_bar_panel_set_width(panel, 400);

	item = gowl_bar_panel_add_hero(panel, "☂", "Umbrella", "Staying dry");
	gowl_bar_panel_item_set_id(item, "power");     /* adds a switch */
	gowl_bar_panel_item_set_active(item, TRUE);

	gowl_bar_panel_add_field_pair(panel, "Ping", "9.8 ms",
	                              "Loss", "0%");
	gowl_bar_panel_add_separator(panel);
	gowl_bar_panel_add_slider(panel, "level", "Level", 0.4);

	item = gowl_bar_panel_add_buttons(panel, "action");
	gowl_bar_panel_add_button(item, "Up", FALSE);
	gowl_bar_panel_add_button(item, "Down", FALSE);

	return panel;
}
#+end_src

Item kinds: =HERO=, =SECTION=, =LABEL=, =FIELD=, =FIELD_PAIR=, =SEPARATOR=, =SLIDER=, =TOGGLE=, =BUTTONS=, =ROW=, =PROGRESS=, =GRAPH=, =CALENDAR=, =SPACER=.

=LABEL= wraps and takes the height its text needs, so an explanation in a panel can be a sentence rather than a truncated line.

The =action= callback is given the item's id, a child index for a button row, and a slider's new value. Rows in a list all share one id unless you give each a distinct one --- the shipped plugins encode the payload into the id (=connect:SSID=, =peer:100.x.y.z=) because the callback sees nothing else.

=build_panel= is called every time the panel is shown *or refreshed*, so it must be cheap and must not block. Refresh it from a poll with =gowl_bar_plugin_refresh_panel()=.

*** Loading, reloading, unloading

:END:

#+begin_src sh
gowl bar-widgets                    # the laid-out bar, per slot and region

gowl bar-plugin-load ~/x/thing.c    # load one now, by path

gowl bar-quarantined                # what is being held back, and why
gowl bar-plugin-clear pomodoro      # let a held-back plugin load again
#+end_src

*** Where plugins are found

Every directory in the search path is scanned at startup, in name order,
and is also what a bare plugin *name* resolves against. The path, in
order of precedence:

1. the =plugin-dir= setting (=plugin-path= is accepted as a synonym) --- colon-separated, so a config can name several
2. =$GOWL_BAR_PLUGIN_DIR=, which is what a development tree wants
3. =$XDG_CONFIG_HOME/gowl/bar-plugins= (=~/.config/gowl/bar-plugins=)
4. =$XDG_DATA_HOME/gowl/bar-plugins= (=~/.local/share/gowl/bar-plugins=)
5. =/usr/local/share/gowl/bar-plugins= and =/usr/share/gowl/bar-plugins=

A configured directory *adds to* the search path rather than replacing
it, so naming one does not cost you the plugins already in
=~/.config=. Each directory is scanned at most once, however the path is
rebuilt.

A name resolves to =<name>=, then =<name>.so=, then =<name>.c= in each
directory in turn. Compiled wins over source in the same directory: the
object is what you last built, and quietly preferring the source would
recompile over the top of it. A spec containing =/= is a path, taken as
written and never searched for --- so a plugin you name explicitly
cannot be shadowed by a same-named one earlier in the path. When nothing
matches, the error names every directory it looked in.

#+begin_src conf
[bar]
plugin-dir = ~/src/mybar/plugins:/opt/gowl/plugins
plugins = weather stocks          # bare names, resolved as above
widgets-right = weather clock battery
#+end_src

=plugins= is loaded *before* the widget lists are read, so a plugin named
there is registered by the time =widgets-right= mentions it. The other
order silently drops the widget: an unknown widget name is skipped rather
than being an error, which is right for a typo and wrong for a plugin
that simply had not loaded yet. A =plugins= entry that does not resolve
is a warning naming the directories searched --- a plugin you asked for
by name and did not get is not something to discover from an empty space
on the bar.


A =.c= file is compiled to a cached shared object keyed on a hash of its contents and its flags, so an unchanged source loads without invoking the compiler. Set =CRISPY_PARAMS= in the source for extra flags:

#+begin_src C
#define CRISPY_PARAMS "$(pkg-config --cflags --libs json-glib-1.0)"
#+end_src

Unloading removes the plugin from the registry and drops every instance of it, but the shared object itself *stays mapped*. Unmapping code that a queued worker or a pending callback may still point into is how a hot-unload turns into a crash somewhere else entirely, and the memory saved is a few tens of kilobytes.

That is also why the vtable form is the one to use: a =GType= cannot be unregistered, so a plugin that defines its own class can be dropped from the bar but a recompiled version of it cannot re-register the same class name.

** When a widget does not appear
:PROPERTIES:
:CUSTOM_ID: missing-widgets
:END:

=gowl bar-widgets= prints the laid-out bar --- each slot, then each widget with its region, its spec and its current label:

#+begin_example
top     enabled visible anchor=clock
  left   tags                         1/3/1
  left   title                        cmacs-gowl.el
  center clock                        Mon Sep 07  11:27
  right  cpu                          CPU 31%
  right  memory                       MEM 11.9G
  right  battery                [off]
  right  tailscale                    set up
bottom  enabled visible anchor=-
  right  ip                           10.0.5.239
#+end_example

"Why is my widget missing" has three plausible answers, and this is what tells them apart:

- *It is not in the list at all.* The spec did not resolve to a registered plugin --- a typo, or a plugin that failed to load. Check =gowl bar-plugins= and =gowl bar-quarantined=.
- *It is listed but marked =[off]=.* The plugin is saying it has nothing to show on this host: no battery on a desktop, no swap, no wireless interface, no Tailscale installed. That is deliberate --- most widgets hide rather than show a blank.
- *It is listed but marked =[hidden]=.* It has something to show but did not fit; the bar dropped it rather than drawing it over its neighbour.
- *It is in the wrong region.* Usually a configuration that set only some regions on top of a layout it expected to be cleared. See [[#shipped-layout][What happens to the shipped layout]].

From Elisp, =M-x cmacs-gowl-bar-widgets=.

** Containment
:PROPERTIES:
:CUSTOM_ID: containment
:END:

Bar plugins run *inside the compositor*. That is what lets them read compositor state directly and draw into the bar's own buffer, and it is also what makes a bad one dangerous: under =emacs --gowl= the compositor is the whole session.

Two mechanisms narrow that.

*** The fault guard
:PROPERTIES:
:CUSTOM_ID: the-fault-guard
:END:

Every call into a plugin --- poll, async poll, draw, click, panel build, panel action, and the load itself --- runs under a signal guard. A =SIGSEGV=, =SIGBUS=, =SIGFPE=, =SIGILL= or =SIGABRT= raised inside one of those calls unwinds back to the call site; the bar then quarantines the plugin, drops it, and raises a critical toast naming it. The session keeps running.

=SIGABRT= is in the set deliberately: =g_assert= and =g_error= are the most likely way a plugin dies, and losing a session to somebody's failed assertion is exactly the outcome this exists to prevent.

The honest limits: this recovers a fault whose damage was confined to the faulting call. A plugin that corrupts the heap and crashes later, somewhere else, is not recoverable by any in-process mechanism. Outside a guarded call the previous handler runs unchanged, so genuine compositor crashes still produce a core dump.

*** The load journal
:PROPERTIES:
:CUSTOM_ID: the-load-journal
:END:

The case the guard cannot catch is the one where the session dies anyway. Before each plugin load the bar writes what it is about to load to =$XDG_STATE_HOME/gowl/bar-plugins.journal=, and clears the entry when the load completes. On the next start, an entry that was never cleared identifies a plugin that took the session down --- so it is quarantined before it gets a second try, and you are told which one it was.

Without that record the next start loads it again and crashes again. With it, one bad session is followed by a notification naming the culprit.

Clear a quarantine with =gowl bar-plugin-clear <name>= once you have fixed the plugin.

** Source guards
:PROPERTIES:
:CUSTOM_ID: source-guards
:END:

=tests/test-bar-guard.sh= (run by =make test=) asserts five properties that no unit test can reach and that all fail silently:

1. Every plugin entry point still runs under the fault guard.
2. The registry still keeps unloaded modules resident rather than closing them.
3. Panels and toasts still use the OVERLAY scene layer, so they float over fullscreen windows.
4. No shipped plugin hard-codes a colour.
5. No shipped plugin spawns synchronously --- that would be on the compositor's dispatch thread.
