* Per-Device Input Remapping
:PROPERTIES:
:CUSTOM_ID: input-remap
:END:
** Overview
:PROPERTIES:
:CUSTOM_ID: input-remap-overview
:END:
Some input devices should have their keys, buttons or sticks mean something else --- /on that device only/. A USB foot pedal that presents itself as a HID keyboard sends =KEY_A= and =KEY_B=; remapping those globally would break the real keyboard. gowl remaps per *physical device*: a rule names the devices it applies to, and every other keyboard or mouse that sends the same codes is untouched.

The feature has three parts:

- *=GowlInputRemapper=* --- an interface the core asks two questions: /does this device need to be claimed?/ and /what does this input on a claimed device turn into?/
- *The core* --- keeps claimed keyboards out of the shared keyboard group, hears them on their own listeners, and delivers what the remapper decides through the compositor's normal key and button decisions.
- *The =inputremap= module* --- the opt-in implementation: rules from the YAML =input-remap:= section, the C config, and runtime rules over IPC, MCP, D-Bus and Elisp.  It also owns the *virtual gamepads* (see [[#input-remap-virtual-pad][Virtual pads]]).

Game controllers take part on both sides.  As *sources*, a gamepad's buttons and stick directions map to keys, clicks and actions like a pedal's, and a stick can move the pointer or scroll (see [[#input-remap-controllers][Game controllers as sources]]).  As *outputs*, keys and the mouse can drive a virtual gamepad that a game reads like a real one.

With the module not loaded, the compositor's input path is exactly what it was before the feature existed. Every hook is a =NULL= check that returns before touching any state, and =tests/test-input-remap-fastpath.sh= holds that in place.

*** The one-to-one rule
:PROPERTIES:
:CUSTOM_ID: input-remap-one-to-one
:END:
Every remap is *one physical press to at most one output*, and the release mirrors the press. There are no sequences, delays, timers, generated repeats, or input sent to an unfocused window. This is enforced by the API, not merely documented:

- A rule maps each input to exactly *one* target. The mapping functions /replace/; there is no append.
- No target kind can hold a list, a delay or a repeat.
- The YAML loader refuses a list as a target, two target kinds in one entry, and any =sequence=, =delay=, =repeat=, =keys=, =then=, =chain=, =times=, =tap=, =hold=, =timeout=, =interval= or =script= key, with =GOWL_INPUT_REMAP_ERROR_NOT_ONE_TO_ONE=. (=macro= is refused as a /rule/ key; inside a map entry it names the macro target below.)
- A key target is modifiers plus *one* key (=Super+9=); =a+b= is refused.
- A command target is *one* line; a newline is refused.
- Remapped keys never arm the compositor's key repeat.

The motivation is game input rules such as World of Warcraft's "one keypress, one action": a foot pedal that clicks once per press is a hardware remap, while a pedal that plays a sequence is automation.

*Some targets are outside the guarantee, on purpose and visibly*:

- the callback target (C config, and Elisp in cmacs) and the macro target (={macro: NAME}=, which runs a [[file:macros.org][gowl macro]] on the press) run arbitrary code by design;
- the *continuous* targets --- ={pointer: x}= and ={scroll: vertical}= on a stick, and a virtual stick that follows the mouse (=REL_X: {stick: right}=) --- produce output for as long as their input is deflected: a held stick is many motion events, not one.  They exist because a stick /is/ continuous; there is no one-press reading of "push the stick halfway".  =inputremap-list= names every one of them in its =continuous= field, so nobody has to read the YAML to find them.

The guarantee covers every other target, and the code is trusted to keep to it itself. A pedal that plays a sequence through a macro is automation as far as a game is concerned --- keep macro targets for things around the game, not in it.

What stays inside the guarantee, and is worth saying because it looks analog: a stick /direction/ used as a key (=ABS_X+: {key: KEY_D}=) is one press when it crosses its threshold and one release when it comes back --- see [[#input-remap-thresholds][Stick directions as keys]].  And a key held on a virtual stick (=KEY_W: {stick: left, y: -1}=) is one press to one held state: the stick is deflected while the key is down and centred when it comes up.

** Quick start: the WoW foot pedal
:PROPERTIES:
:CUSTOM_ID: input-remap-quick-start
:END:
The case this was built for: a 2-pedal USB switch.

- *Pedal A* → a middle-mouse click at the cursor. A fishing addon binds middle click to "cast, or loot the bobber", so one press is one action.
- *Pedal B* → jump to WoW: view the tag it lives on and focus it. This is a compositor action; nothing is sent to the game.

*1. Enable the module* (it is opt-in) and add the rule, in =~/.config/gowl/config.yaml=:

#+begin_src yaml
modules:
  inputremap:
    enabled: true
    log: claim

input-remap:
  - name: wow-pedals
    match:
      id: "1a86:e026"      # from inputremap-devices; see step 2
      type: keyboard
    unmatched: drop
    log: true
    map:
      KEY_A: { button: middle }
      KEY_B: { action: focus-client, arg: "title:World of Warcraft*" }
#+end_src

*2. Find the pedal's identity.* Plug it in and ask:

#+begin_src bash
gowl-msg inputremap-devices
#+end_src

#+begin_src bash
gowl-msg inputremap-identify 10
#+end_src

Press a pedal within ten seconds, then:

#+begin_src bash
gowl-msg inputremap-identify-result
#+end_src

The result names the device (with its =vendor-product=) and the input it sent (=KEY_A=), which is exactly what the rule's =match:= and =map:= need. Identify mode only observes: the press still goes wherever it was going.

*3. Reload* (=Super+Shift+r=, or =gowl-msg reload=). The pedal is claimed at once; the log shows it:

#+begin_example
2026-09-28T12:00:00-04:00 inputremap: claimed device 12 keyboard 1a86:e026 event19 "PCsensor FootSwitch"
#+end_example

The same example ships as =data/example-input-remap.yaml=, and as C config in =data/example-input-remap.c=, where pedal B is a callback that launches WoW when it is not running. Both are installed to =$(DATADIR)/gowl/=.

** Rules
:PROPERTIES:
:CUSTOM_ID: input-remap-rules
:END:
A rule has a name, a =match:= block saying which devices it applies to, and a =map:= of inputs to targets.

#+begin_src yaml
- name: NAME              # required; also the id used to remove it
  match:                  # required; at least one of name/id/vendor/product/sysname
    name: "GLOB"          # libinput device name, * and ? only
    id: "VVVV:PPPP"       # vendor:product in hex, as lsusb prints it
    vendor: 0x1a86        # or separately (always hex)
    product: e026
    sysname: "event*"     # kernel sysname
    type: keyboard        # keyboard | pointer | gamepad | joystick | any (default any)
  unmatched: pass         # pass (default) | drop: inputs the map does not name
  log: false              # log every remap this rule makes
  grab: false             # game controllers: take the device from everything else
  analog: { ... }         # game controllers and virtual sticks: see Analog settings
  virtual-pad: { name: NAME }   # the gamepad stick/trigger/pad-button targets drive
  map:
    INPUT: TARGET
#+end_src

*** Matching
:PROPERTIES:
:CUSTOM_ID: input-remap-matching
:END:
Every criterion the rule sets must hold; unset criteria are ignored. A rule with /no/ criterion matches nothing --- a rule that matched everything would claim the keyboard being typed on --- and is refused by the loader. =type= narrows but is not a criterion on its own.

Vendor and product come from libinput (=libinput_device_get_id_vendor/product=, through =wlr_libinput_get_device_handle()=). They are the most specific identity and the one to prefer. Many pedals are /composite/ devices that expose a keyboard and a pointer with the same ids; =type:= picks one.

A rule may match several devices, and a device may be matched by several rules (see [[#input-remap-priority][Priority]]).

*** Inputs
:PROPERTIES:
:CUSTOM_ID: input-remap-inputs
:END:
| Form                                        | Example                  |
|---------------------------------------------+--------------------------|
| Any evdev key or button name                | =KEY_A=, =KEY_F13=, =BTN_SIDE= |
| Friendly button names                       | =left=, =middle=, =right=, =side=, =extra=, =forward=, =back=, =task= |
| Wheel notches (pointers)                    | =WHEEL_UP=, =WHEEL_DOWN=, =WHEEL_LEFT=, =WHEEL_RIGHT= |
| Raw evdev codes                             | =30=, =0x110=            |
| Gamepad buttons (any =BTN_*=, or a friendly name) | =BTN_SOUTH=, =pad-a=, =left-bumper= |
| A stick or hat direction (digital)          | =ABS_X+=, =ABS_Y-=, =left-stick-up=, =dpad-left= |
| A whole axis (continuous targets only)      | =ABS_RX=, =right-stick-x=, =left-trigger= |
| Pointer motion (stick-follow targets only)  | =REL_X=, =REL_Y=, =mouse-x=, =mouse-y= |

The evdev names come from the kernel headers at build time (=gowl-evdev-names.inc=, generated from =<linux/input-event-codes.h>=), so every =KEY_*= and =BTN_*= the kernel defines is accepted. Names are case-insensitive.

A wheel notch counts in whole notches (120 value120 units), so a high-resolution wheel's quarter-notches add up to /one/ input, not four. Each notch is a press immediately followed by its release. Touchpad (continuous) scrolling is never remapped.

*** Targets
:PROPERTIES:
:CUSTOM_ID: input-remap-targets
:END:
| Target                                  | What one press does                                      |
|-----------------------------------------+----------------------------------------------------------|
| =pass=                                  | Deliver the input unchanged                              |
| =drop=                                  | Swallow it                                               |
| ={key: "Super+9"}=                      | One key to the focused client, modifiers held for it     |
| ={key: KEY_F13}=                        | One key by keycode (layout-independent)                  |
| ={button: middle}=                      | One pointer button at the current cursor position        |
| ={action: tag-view, arg: "256"}=        | One compositor action, on press                          |
| ={command: "scratchpad-toggle"}=        | One command line through module IPC, on press            |
| ={macro: sort-windows, args: "x"}=      | Run a gowl macro, on press (outside one-to-one)          |
| ={pointer: x}= (whole axis only)        | Move the pointer while the stick is deflected (continuous) |
| ={scroll: vertical}= (whole axis only)  | Scroll in wheel notches while deflected (continuous)     |
| ={stick: left, x: -1}=                  | Hold the virtual pad's stick left while held             |
| ={stick: right}= (=REL_X=/=REL_Y= only) | The virtual stick follows the mouse (continuous)         |
| ={trigger: right, value: 1.0}=          | Pull the virtual pad's trigger while held                |
| ={pad-button: BTN_SOUTH}=               | Hold the virtual pad's button while held                 |
| /callback/ (C, and Elisp in cmacs)      | Arbitrary code, on press and on release                  |

- *Keys.* A keysym (=Page_Up=, =9=) is resolved against the live keymap at the moment of the press; if the symbol sits on a shifted level, Shift is added. A =KEY_*= name is the keycode itself. Modifiers are held in the shared xkb state for the key and released with it, and a modifier that is already physically held is not pressed twice.
- *Buttons.* A press and release at wherever the cursor is, through the same decision a real click takes: click-to-focus, the bar, mousebinds and module mouse handlers all see it.
- *Actions.* Any =GOWL_ACTION_*= by its nick (the same names as keybinds, =_= or =-=), through the normal keybind dispatch. The release does nothing.
- *Commands.* One line for =gowl_compositor_run_command()= --- a module IPC word such as =scratchpad-toggle=. In cmacs, =custom= actions are how Elisp is reached (see the cmacs manual).
- *Macros.* =macro-run --trigger=remap --detail='RULE INPUT' NAME ARGS= through the macro module, on the press; the release is swallowed, and nothing runs while the session is locked. =args= is one shell-parsed command line. The macro module must be loaded; without it the press is logged and dropped. In C: =gowl_input_remap_rule_map_macro(rule, input, name, args, &error)=. See [[file:macros.org::#macros-remap][macros.org]].

=focus-client= is an action added alongside this feature, and useful on its own: =focus-client app-id:GLOB= or =focus-client title:GLOB= (a bare glob is an app-id) views the first matching window's tags, selects its monitor and focuses it. It is what lets pedal B say "take me to the game" without knowing which tag the game is on.

*** Priority
:PROPERTIES:
:CUSTOM_ID: input-remap-priority
:END:
Rules come from two layers: the *config* layer (the =input-remap:= list, replaced wholesale on reload) and the *runtime* layer (=inputremap-add= and friends). A runtime rule shadows a config rule of the same name.

For one input on one device, the rules are walked newest first --- runtime before config, later before earlier --- and the first rule that /matches the device and mentions the input/ decides it. When no matching rule mentions the input, the highest-priority rule that matches the device decides by its =unmatched:= setting. When no rule matches the device, it is not claimed at all.

** Game controllers as sources
:PROPERTIES:
:CUSTOM_ID: input-remap-controllers
:END:
A gamepad is not a libinput device: udev tags it =ID_INPUT_JOYSTICK=, libinput leaves it alone, and games open =/dev/input/eventN= themselves.  So the compositor never sees one --- until a rule asks for it.  Then the core (=src/core/gowl-input-remap-pad.c=) finds it, reads it, and feeds what it does through the same decisions a pedal's keys take.

*** Finding them
:PROPERTIES:
:CUSTOM_ID: input-remap-controllers-discovery
:END:
- Nothing happens without an active remapper: no scan, no watch, no open.  =tests/test-input-remap-fastpath.sh= holds it.
- With one, the core reads =/sys/class/input/event*= --- the name, the =id/vendor= and =id/product=, the capability bitmaps --- *without opening anything*, and watches =/dev/input= with inotify for hotplug.  No libudev: gowl does not link it, and sysfs plus inotify is all it needs.
- A node is a *gamepad* when it has the gamepad buttons (=BTN_SOUTH= and friends), a *joystick* when it has joystick buttons, or X/Y plus a joystick-only axis (Z, RX, RY, RZ, throttle, rudder, hats).  Anything with a pen, a touch, =BTN_0= (a tablet pad) or relative axes (a mouse) is libinput's, and so is any node libinput already has open.
- gowl's own virtual pads (named =gowl virtual pad: ...=) are never read back.
- A keyboard can have a joystick node of its own --- the ZSA Voyager exposes one --- and it is simply another device, with its own =event= node and the keyboard's vendor:product; =type: joystick= picks it.

*** Opening them
:PROPERTIES:
:CUSTOM_ID: input-remap-controllers-open
:END:
A controller is *opened only when a rule claims it* --- the same =match:= as any other device, with =type: gamepad= or =type: joystick= to narrow it.  It is opened through the compositor's seat session (libseat: logind or seatd hand over the fd, and revoke it when the VT is left) when gowl runs as a session, else with a plain =open()=.  gowl never opens one as root without a session.

The one exception is *identify mode*: while =inputremap-identify= listens, every controller is open read-only and never grabbed, so pressing a button or pushing a stick on one no rule names yet tells you its codes.  Identify ends, and they are closed.

*** Grab
:PROPERTIES:
:CUSTOM_ID: input-remap-controllers-grab
:END:
=grab: true= on the rule that decides a controller takes it with =EVIOCGRAB=: while gowl holds it, nothing else reads it --- the game included.  That is the point when the controller is remapped /for/ the game (its stick turned into keys, say), and the reason it is off by default: merely matching a controller must never take it away from a game.  Releasing the claim (rule removed, module disabled) releases the grab.

A device's =grab= and =analog= settings come from the *highest-priority rule that matches it*, the same rule whose =unmatched:= applies.

*** Analog settings
:PROPERTIES:
:CUSTOM_ID: input-remap-analog
:END:
#+begin_src yaml
analog:
  deadzone: 0.15        # default: the device's own `flat', at least 0.05
  press: 0.5            # a stick direction presses here...
  release: 0.35         # ...and releases below here (must be lower)
  invert: [ABS_Y]       # axes read reversed
  centred: [ABS_Z]      # an axis starting at 0 that rests in the middle
  pointer-speed: 1200   # px/s at full deflection
  pointer-curve: 2.0    # speed = deflection ^ curve: fine near the centre
  pointer-accel: 0.0    # extra speed per second held, as a fraction (cap 4x)
  scroll-rate: 8        # wheel notches/s at full deflection
  mouse-gain: 0.02      # virtual-stick deflection per pixel of mouse motion
  mouse-idle-ms: 100    # a mouse-driven stick recentres this long after the mouse stops
  slant: 0              # degrees toward +X a vertical push reads as; see below
  gate: 0               # drop the lesser axis of a near-straight push; 0 keeps both
#+end_src

Every axis is calibrated from =EVIOCGABS= (min, max, flat, fuzz) and normalised: sticks and hats to [-1, 1], split at the middle of their range so =0..255= resting at 128 and =-32768..32767= read the same; triggers (=ABS_Z=, =ABS_RZ=, gas, brake, throttle with an unsigned range) to [0, 1].  Inside the deadzone an axis is 0; beyond it the remaining travel is rescaled, so the output still runs smoothly from 0.  The loader refuses a deadzone above 0.95, a release at or above the press threshold, a slant outside [-60, 60], a gate outside [0, 1], and out-of-range speeds and curves.

=slant= is for a stick whose straight up *and* straight down both read toward +X (a thumb that pushes the stick off to the right of the pad).  The angle is removed from X in proportion to |Y| (=x - |y| * tan(slant)=), so both of those pushes come back onto Y.  It is not a rotation.  Rotating the pair until up lies on Y swings down onto +X, and down then holds the right-hand key.  A real diagonal, past that angle, still has X left and still presses both keys.  =slant= applies to the left stick (=ABS_X=/=ABS_Y=) and the right stick (=ABS_RX=/=ABS_RY=) only.  Hats and triggers are unchanged.  The corrected deflection is what a pointer or scroll target sees.

=gate= is only the digital edges.  When the lesser axis is under =gate= times the greater, it is not pressed, so a push a few degrees off a cardinal stays one key.  0, the default, presses every axis that crosses =press=, and a diagonal is two keys.  An equal pair is never dropped.  Pointer and scroll keep the ungated value, so a stick used as the mouse does not snap to the cardinals.

*** Stick directions as keys
:PROPERTIES:
:CUSTOM_ID: input-remap-thresholds
:END:
=ABS_X+= is the stick pushed right, =ABS_X-= left; on a hat (the d-pad) the same.  A direction is *pressed* when the axis crosses =press= and *released* when it falls back below =release=: the gap is hysteresis, so a stick resting near the threshold does not chatter a key on and off.  One crossing is one press, routed through the ordinary key/button/action targets, so everything those guarantee --- the release mirroring the press, no repeats, the lock-aware pipelines --- holds.  Opposite directions of one axis are independent inputs; a diagonal is two keys, as on a keyboard.

A bare axis name given a digital target means its positive direction: =right-trigger: {button: left}= clicks when the trigger is pulled past =press=.

*** Sticks as the pointer
:PROPERTIES:
:CUSTOM_ID: input-remap-continuous
:END:
A *whole* axis can take =pointer: x|y= or =scroll: vertical|horizontal=.  While it is out of its deadzone, an 8 ms tick on the compositor's event loop moves the pointer at =pointer-speed × deflection^pointer-curve= (plus =pointer-accel= for each second held), or scrolls whole wheel notches (value120, 120 each) at =scroll-rate=.  When every such axis is centred the tick is not re-armed: *no timer runs at rest*.

The motion takes the path real relative motion takes (=compositor_handle_motion_relative()=): a locked pointer stays put and its client reads the relative stream, a confined one slides along its region, InputCapture sees it at a barrier, and the recorder records it.  The scroll goes through the same decision a wheel's does --- recorder, mousebinds, the bar, module handlers, the client.  These are the declared continuous exceptions (see [[#input-remap-one-to-one][the one-to-one rule]]).

** Virtual pads
:PROPERTIES:
:CUSTOM_ID: input-remap-virtual-pad
:END:
Wayland has no gamepad protocol: a game reads its controllers from =/dev/input=.  The only way to give a game a stick is a real input device, so the module makes one through =/dev/uinput= --- a *virtual pad*.

#+begin_src yaml
virtual-pad:
  name: game                 # the device is "gowl virtual pad: game"
  id: "1209:0007"            # default: pid.codes' test range
  buttons: [BTN_SOUTH, BTN_EAST]          # default: an Xbox-style set
  axes: [ABS_X, ABS_Y, ABS_Z, ABS_RX, ABS_RY, ABS_RZ, ABS_HAT0X, ABS_HAT0Y]
#+end_src

- A rule declares at most one pad, and its =stick=, =trigger= and =pad-button= targets drive it; the loader refuses those targets in a rule that declares none.  Rules naming the same pad share one device (the first declaration's layout).
- It is *created lazily*, on the first press that drives it --- loading a rule makes nothing --- and *destroyed* when no rule declares it any more, when the module is disabled, and when the compositor stops.  =tests/test-input-remap-uinput-guard.sh= holds every way out.
- Sticks report =-32768..32767=, triggers =0..255=, the d-pad hat =-1..1=, bus =BUS_VIRTUAL=.
- *Keys onto a stick*: each held input contributes its deflection, and the stick is derived from what is held.  Opposite directions cancel (both held is centre); W+D is up-right *normalised onto the unit circle*, not the corner --- a game reading the magnitude would otherwise move 41% faster diagonally.  Releasing a key takes back exactly its contribution.  This is one press to one held state: inside the one-to-one rule.
- *The mouse onto a stick* (=REL_X: {stick: right}=, =REL_Y: {stick: right}=): each motion event deflects the stick by =mouse-gain= per pixel, and a timer returns it to centre =mouse-idle-ms= after the mouse stops.  The cursor does not move for a component a rule takes.  Continuous: a declared exception.
- Nothing new is pressed on a virtual pad while the session is locked (a pad reaches a game without passing the lock screen); releases still go through.

*** Permissions
:PROPERTIES:
:CUSTOM_ID: input-remap-permissions
:END:
- *Reading a controller* needs read access to its =/dev/input/eventN=.  On a desktop, udev's =uaccess= tag gives the logged-in user an ACL on joystick nodes; under a seat session gowl asks libseat instead, which needs no ACL.
- *Making a virtual pad* needs write access to =/dev/uinput=.  Many distributions grant it to the active session by a =uaccess= rule (=getfacl /dev/uinput= shows =user:YOU:rw-=); otherwise a udev rule such as =KERNEL=="uinput", TAG+="uaccess"=, or the =input= group.
- *Without it*, the rule still loads.  The first press logs the reason once (=cannot open /dev/uinput: Permission denied (needs write access ...)=), the socket gets =EVENT inputremap pad-error NAME=, =inputremap-status= carries =pad-error="..."=, and nothing else happens --- no crash, no retry loop.
- The live session's remapper only ever opens a controller a rule matches, so a test pad (=1209:0008=, say) is invisible to it unless one of your rules names that id.

*** Worked examples
:PROPERTIES:
:CUSTOM_ID: input-remap-pad-examples
:END:
*Left stick as WASD* --- a game that only takes the keyboard, played on a pad, with the pad hidden from the game:

#+begin_src yaml
input-remap:
  - name: stick-wasd
    match: { id: "045e:028e", type: gamepad }
    grab: true
    analog: { press: 0.5, release: 0.3 }
    map:
      left-stick-up:    { key: KEY_W }
      left-stick-left:  { key: KEY_A }
      left-stick-down:  { key: KEY_S }
      left-stick-right: { key: KEY_D }
      pad-a:            { key: KEY_SPACE }
      right-trigger:    { button: left }
#+end_src

*Right stick as the mouse* --- the couch, a browser, a pad:

#+begin_src yaml
  - name: pad-mouse
    match: { id: "045e:028e", type: gamepad }
    analog: { pointer-speed: 1500, pointer-curve: 2.0, scroll-rate: 12 }
    map:
      right-stick-x: { pointer: x }
      right-stick-y: { pointer: y }
      left-stick-y:  { scroll: vertical }
      pad-a:         { button: left }
      pad-b:         { button: right }
#+end_src

*A keypad as a controller* --- a game that only reads gamepads, played from a dedicated keypad while the main keyboard is untouched:

#+begin_src yaml
  - name: keypad-pad
    match: { id: "1234:5678", type: keyboard }
    unmatched: drop
    virtual-pad: { name: keypad }
    map:
      KEY_KP8:     { stick: left, y: -1 }
      KEY_KP2:     { stick: left, y: 1 }
      KEY_KP4:     { stick: left, x: -1 }
      KEY_KP6:     { stick: left, x: 1 }
      KEY_KP0:     { pad-button: BTN_SOUTH }
      KEY_KPENTER: { trigger: right }
#+end_src

*Mouse-look on a controller game* --- a trackball as the right stick:

#+begin_src yaml
  - name: trackball-look
    match: { name: "*Trackball*", type: pointer }
    virtual-pad: { name: look }
    analog: { mouse-gain: 0.03, mouse-idle-ms: 80 }
    map:
      mouse-x: { stick: right }
      mouse-y: { stick: right }
#+end_src

The same rules from C use =gowl_input_remap_rule_set_virtual_pad()= (first), =_map_stick()=, =_map_stick_follow()=, =_map_trigger()=, =_map_pad_button()=, =_map_pointer()=, =_map_scroll()=, =_set_grab()= and =_set_analog()= (start from =gowl_input_remap_analog_init()=).  Inputs are =GOWL_INPUT_REMAP_ABS_INPUT(ABS_X, GOWL_INPUT_REMAP_ABS_POS)= and friends.

*** Friendly names
:PROPERTIES:
:CUSTOM_ID: input-remap-pad-aliases
:END:
| Name                                    | Input                       |
|-----------------------------------------+-----------------------------|
| =left-stick-left= / =-right= / =-up= / =-down= | =ABS_X-= / =ABS_X+= / =ABS_Y-= / =ABS_Y+= |
| =right-stick-left= ... =right-stick-down= | =ABS_RX-= ... =ABS_RY+=    |
| =left-stick-x=, =left-stick-y=          | =ABS_X=, =ABS_Y= (whole)    |
| =right-stick-x=, =right-stick-y=        | =ABS_RX=, =ABS_RY= (whole)  |
| =left-trigger=, =right-trigger=         | =ABS_Z=, =ABS_RZ=           |
| =dpad-up= / =-down= / =-left= / =-right= | =ABS_HAT0Y-= / =ABS_HAT0Y+= / =ABS_HAT0X-= / =ABS_HAT0X+= |
| =pad-a= (=pad-south=), =pad-b= (=pad-east=) | =BTN_SOUTH=, =BTN_EAST=  |
| =pad-x= (=pad-west=), =pad-y= (=pad-north=) | =BTN_WEST=, =BTN_NORTH=  |
| =left-bumper=, =right-bumper=           | =BTN_TL=, =BTN_TR=          |
| =left-trigger-button=, =right-trigger-button= | =BTN_TL2=, =BTN_TR2=  |
| =pad-select=, =pad-start=, =pad-guide=  | =BTN_SELECT=, =BTN_START=, =BTN_MODE= |
| =left-stick-press=, =right-stick-press= | =BTN_THUMBL=, =BTN_THUMBR=  |
| =mouse-x=, =mouse-y=                    | =REL_X=, =REL_Y=            |

Button names are *positional*, as the kernel's gamepad documentation defines them: =BTN_SOUTH= is the bottom face button whatever its label (A on Xbox, Cross on PlayStation, B on Nintendo).  Drivers have not always agreed about =BTN_X=/=BTN_Y=; run =inputremap-identify= and press the button to see what yours sends.  Pad aliases carry a =pad-= prefix so =a= and =x= stay free for keyboard keys.

** How it works
:PROPERTIES:
:CUSTOM_ID: input-remap-internals
:END:
*** The interface
:PROPERTIES:
:CUSTOM_ID: input-remap-interface
:END:
#+begin_src C
struct _GowlInputRemapperInterface {
	GTypeInterface parent_iface;

	gboolean             (*claims_device)  (GowlInputRemapper          *self,
	                                        const GowlInputDeviceInfo  *info);
	GowlInputRemapRule  *(*map_event)      (GowlInputRemapper          *self,
	                                        const GowlInputDeviceInfo  *info,
	                                        const GowlInputRemapEvent  *event,
	                                        const GowlInputRemapTarget **out_target);
	void                 (*device_changed) (GowlInputRemapper          *self,
	                                        const GowlInputDeviceInfo  *info,
	                                        gboolean                    claimed);
	gboolean             (*render_pad)     (GowlInputRemapper          *self,
	                                        GowlInputRemapRule         *rule,
	                                        const GowlInputRemapTarget *target,
	                                        const GowlInputRemapEvent  *event,
	                                        gdouble                     amount);
};
#+end_src

=GowlInputDeviceInfo= is a plain value (id, type, name, sysname, vendor, product, claimed), so rules are matched and tested without wlroots. =map_event= returns the deciding rule (a reference) and its one target; =NULL= means pass. The module manager classifies implementations like every other interface; =gowl_module_manager_get_input_remapper()= returns the first *active* one.  =render_pad= (optional) receives the stick, trigger and pad-button targets: the core keeps the held table and the lock rule, the implementation owns the virtual pads.

A game controller has no =wlr_input_device=, so the core gives it a /device-less/ record (=gowl_input_remap_core_source_new()=); its edges arrive as =GOWL_INPUT_REMAP_EVENT_PAD= through =gowl_input_remap_core_source_edge()= and take the same decide / held / release path as a pedal's.  Motion on a claimed pointer is offered first to =gowl_input_remap_core_motion()= (=REL_X=/=REL_Y= inputs), which is =NULL=-fast when nothing is claimed.

*** Claiming a keyboard
:PROPERTIES:
:CUSTOM_ID: input-remap-claim
:END:
Every keyboard normally joins one =wlr_keyboard_group=, which is what lets a modifier held on one keyboard apply to another --- and what makes it impossible to tell which device a key came from. So:

1. On hotplug, =create_keyboard()= asks =gowl_input_remap_core_try_claim()= before adding the keyboard to the group. It returns =FALSE= at once when no remapper is active.
2. A claimed keyboard keeps its own keymap and xkb state, stays *out* of the group, and is heard on its own =events.key= listener. Its keys never reach the shared state until the remapper has decided what they are.
3. The decided output is fed into the group's xkb state and through =compositor_handle_key()= --- the same decision real keys take: configured keybinds, module keybinds, the embedder intercept, InputCapture, then the focused client.
4. The seat keeps its keyboard capability when the only keyboard is a claimed pedal.

A pointer is never detached: =wlr_cursor= already passes every button with its device, so a claimed pointer stays attached (motion is untouched) and only its buttons and wheel notches are offered to the remapper, from =on_cursor_button= and =on_cursor_axis=.

*** Claim and release lifecycle
:PROPERTIES:
:CUSTOM_ID: input-remap-lifecycle
:END:
| Event                               | What happens                                                        |
|-------------------------------------+---------------------------------------------------------------------|
| Device plugged in                   | Asked once; claimed or joins the group                              |
| Rule added / removed / replaced     | The module calls =gowl_compositor_input_remap_reevaluate()=         |
| Module enabled / disabled           | Re-evaluated; disabling releases everything                         |
| Config reloaded                     | Re-evaluated against the new config's rules                         |
| Device unplugged                    | Anything it held is released; its record freed                      |
| Controller node deleted (inotify)   | The same: released, its grab and fd gone                            |
| VT left / regained (seat session)   | The session revokes controller fds; =active= re-opens them           |
| Compositor teardown                 | =gowl_input_remap_core_finish()= drops every record and listener    |

Re-evaluation walks every connected device. A newly claimed keyboard leaves the group --- wlroots releases on the group any key it still held, so nothing is stuck --- and a released one rejoins.

*The release mirrors the press.* What each press produced is recorded (with a reference to its rule, which keeps the target alive), and its release replays exactly that. A rule removed or replaced while a pedal is down cannot strand a key or a button: releasing a device flushes everything it holds.

*** Ordering, recording and capture
:PROPERTIES:
:CUSTOM_ID: input-remap-ordering
:END:
Remapped output is *real* input, not synthetic: it came from hardware. So:

- The input recorder records what the session received (the remapped key or click, not the pedal's raw code).
- An active InputCapture (this machine as KVM server) carries remapped keys and buttons to the other machine, like any local input. Actions, commands and callbacks run locally.
- Key repeat is the one difference: it is never armed for a remapped key (=remap_feeding= in =compositor_handle_key()=).

*Super+Escape stays an escape hatch.* On a claimed keyboard, Escape pressed while that device holds Super bypasses every rule and is delivered as Super[+Shift]+Escape, so the InputCapture break and the recorder's Super+Shift+Escape force-stop always work.

*While the session is locked*, actions, commands and callbacks do not run; keys and buttons go through the lock-aware pipelines, which only let lock-screen input through.

** C config
:PROPERTIES:
:CUSTOM_ID: input-remap-c-config
:END:
The rule model is part of libgowl, so a C config (compiled at startup, before any module loads) builds rules directly:

#+begin_src C
GowlInputRemapRule *rule;
GError             *error = NULL;

rule = gowl_input_remap_rule_new("wow-pedals");
gowl_input_remap_rule_set_match_ids(rule, 0x1a86, 0xe026);
gowl_input_remap_rule_set_match_type(rule, GOWL_INPUT_REMAP_DEVICE_KEYBOARD);
gowl_input_remap_rule_map_button(rule, KEY_A, BTN_MIDDLE, &error);
gowl_input_remap_rule_map_action(rule, KEY_B, GOWL_ACTION_FOCUS_CLIENT,
                                 "title:World of Warcraft*", &error);
gowl_config_add_input_remap_rule(gowl_config, rule);
gowl_input_remap_rule_unref(rule);
#+end_src

=gowl_input_remap_rule_map_callback()= maps an input to a C function, called on the compositor thread on press and on release:

#+begin_src C
static void
on_pedal(
	GowlInputRemapRule        *rule,
	const GowlInputRemapEvent *event,
	GowlCompositor            *compositor,
	gpointer                   user_data
){
	if (event->pressed)
		gowl_compositor_run_command(compositor, "scratchpad-toggle");
}

gowl_input_remap_rule_map_callback(rule, KEY_C, on_pedal, NULL, NULL);
#+end_src

A compiled config that maps a callback is kept loaded for the life of the session: the compositor holds a pointer into it, and closing it on reload would leave a pedal press jumping into unmapped memory. The config compiler notices (=gowl_input_remap_callback_generation()=) and makes that one config resident.

** Limits
:PROPERTIES:
:CUSTOM_ID: input-remap-limits
:END:
- A remapped key's modifiers are pushed through the shared xkb state and =wl_keyboard.modifiers=, not a group =modifiers= signal; an input method grab sees the key but not a separate modifier event, as with injected keys.
- Pointer motion is remapped only onto a virtual stick (=REL_X=/=REL_Y=); touchpad scrolling never is.
- Controllers are read on Linux only (evdev, uinput and inotify; the build probes for them, =EVDEV_PADS=0= turns them off).  Elsewhere the rest of the remapper is unchanged and controller rules match nothing.
- An axis that starts at 0 is read as a trigger, except ABS_X/Y/RX/RY and hats; a cheap pad that puts its right stick on =ABS_Z= needs =analog: {centred: [ABS_Z]}=.
- One rule's =analog:= and =grab:= apply to a whole device: the highest-priority rule matching it.
- Virtual pads report =BUS_VIRTUAL=; a game with a hard-coded controller list may want a real vendor:product in =id:=.
- Force feedback (rumble) is neither read from nor written to virtual pads.
- A device that is not a libinput device (headless, virtual) has no vendor, product or sysname; match it by name.
- Clients repeat a held key themselves (=wl_keyboard.repeat_info=); a remapped key held down repeats in the application exactly as the physical key would. gowl generates none.
